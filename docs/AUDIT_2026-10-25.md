# LobsterOS deep audit: plan vs code, quality of "done" work, execution queue

**Snapshot (2026-10-25):** kernel `f999ea7` (master, clean) · emulator `6c80287` (r42, clean) · qemu-src `bed668c` (**detached HEAD**). This was read-only: nothing was changed, built or run.

**How the evidence was gathered:** I read the code directly, and three parallel read-only sub-audits covered the kernel core, the desktop/apps, and the systems/emulator/testing side. **✔** marks a claim I re-read in the source myself. Unmarked file:line cites come from the sub-audits; all 18 of their claims that I spot-checked held up.

**Sizes:** S ≈ up to 1 agent-day · M ≈ 2–4 days · L ≈ 1–2 weeks.

## Top findings

1. **S3 is not real preemption.** Hardware ticks are armed at boot (`src/lib.rs:949-966` ✔), but on QEMU nothing ever acts on them:
   - The IRQ handler never calls `schedule()` (`arch/exception.rs:330-339`, compiled out by `cfg(not(qemu_raspi5b))` ✔).
   - `on_timer_tick` only sets a flag that nobody reads (`sched/mod.rs:1010-1059` ✔).
   - The only thing that ends an app's time slice is `SYS_SLEEP` (sole caller of `request_slice_yield`: `syscall.rs:1204` ✔).
   - Result: any EL0 program that doesn't sleep (`while(1);`, a long Python loop, buggy user code in the future Code app) freezes the desktop and shell until reboot.
2. **S4 is unsafe by construction: there are no per-process address spaces on QEMU.**
   - Every app's pages are mapped into the one kernel page table (TTBR0) at the same virtual addresses (`sched/elf.rs:404-413, 470-482` ✔).
   - Every process gets the same fixed stack address, `USER_STACK_TOP=0x7F00_0000` (`elf.rs:24` ✔).
   - `run_and_wait` never switches page tables on QEMU (`sched/mod.rs:1302-1304` ✔).
   - So two different apps running at once share or steal each other's code, data and stack pages. The S4 live check most likely passed because it ran two copies of the same demo binary (unverified).
3. **FP/SIMD registers are never saved.**
   - The exception frame is 272 bytes of integer registers only (`boot.S:402-403` ✔).
   - The kernel is built with NEON (`targets/aarch64-lobsteros.json` `+neon`), and the current release ELF contains 204 q/v-register instructions ✔.
   - Every 10 ms tick and every syscall taken from EL0 can therefore corrupt an app's FP/SIMD state, and background apps share those registers across slices.
   - This has been live since 993fefd turned ticks on by default.
4. **Security and memory-safety holes in "done" code:**
   - `sigreturn` restores whatever SPSR the user supplies, so an EL0 app can return into EL1 (`sched/signal.rs:446-458` ✔).
   - The Rust `TrapFrame` is 280 bytes while the asm frame is 272 (`sched/mod.rs:96-109` ✔), so sigreturn writes 8 bytes past the frame.
   - Window and stack frames are freed while still mapped (`wm/user_windows.rs:497-534` ✔).
   - No syscall validates user pointers.
   - The login greeter accepts anyone without a password (`users/mod.rs:87-97` ✔).
5. **The calculator can panic the kernel:** `5 % 0` hits an unguarded remainder (`apps/calculator.rs:91` ✔).
6. **The biggest daily-driver gaps:**
   - The Files window gets no mouse input at all, and Settings gets no input at all (neither has a stage in the event router, `wm/event_router.rs:80-91` ✔).
   - The App Store GUI is an empty mock window (`wm/start_menu.rs:94-102` ✔).
   - Python scripts can't run (`tools/micropython/main.c:83-102` ✔).
   - `shutdown` doesn't work (`drivers/power.rs:329-350` ✔).
7. **The plan is stale beyond the known cases:** B4.1 is done; A4.3 is only partial; A3.1 overstates what's done; E1 has 8 tests, not 5; B8 and B6.4 are only half done.
8. **Repo hygiene:**
   - The lobster commits in qemu-src sit on a detached HEAD that no branch contains ✔, and `e3fdfbe` committed the whole `build-opt/` directory (3,268 files ✔).
   - `src/drivers/rp1.rs` (684 lines, relevant to C9) exists only on the unmerged branch `feat/wifi-shell-enhancements` (`2681b2d` ✔).

## Deliverable 2: Quality audit of the claimed-done work

### 2.1 Does the preemption boot default match the S3 claim?
- **Ticks are armed at boot**, but in `kernel_main`, not in `boot.S` or the GIC init ✔. Under the QEMU build, `lib.rs:949-966` enables PPI 29, sets its priority and edge trigger, opens the priority mask (0xFF), arms the timer with a 500 ms first tick, and calls `set_preempt(true)`. IRQs are unmasked at `lib.rs:969-972`. The handler re-arms every 10 ms (`timer.rs:143-150`). So "PPI 29, 10 ms" is accurate.
- **It is not preemption** (finding 1 above). While a foreground app runs, it busy-waits inside `sys_sleep` and only pumps `wm::tick` (`syscall.rs:1206-1213` ✔), so background apps and the shell starve.
- **What S3 actually delivered**, which is valuable:
  - Exception returns are now safe when a tick arrives, because ELR/SPSR are saved in the frame (`boot.S:433,447-454`).
  - The cooperative-exit offsets are correct (`exception.rs:250-251`).
- **The real-hardware path is different and has never been run on hardware:**
  - It uses the BCM system timer (`lib.rs:943-947`) and calls `schedule()` from the IRQ (`exception.rs:333-339`).
  - That is the very path the code's own comment says corrupts the main loop (`exception.rs:331`).

### 2.2 High severity
- **H1. No real preemption.** See 2.1 → Q5.
- **H2. No address-space isolation.** See finding 2.
  - The argv block is also written through the shared stack mapping (`sched/mod.rs:684-686`), so with two apps it can land in the other app's stack → Q4.
- **H3. FP/SIMD not saved.** See finding 3 → Q3.
- **H4. sigreturn escalation and the oversized TrapFrame (same bug class as the S3 hunt):**
  - The TrapFrame mismatch (finding 4) means sigreturn writes 8 bytes past the frame (`signal.rs:458`) and the signal setup reads 280 bytes (`signal.rs:382-386`).
  - The cooperative exit still writes raw element offsets and the magic value `0x3C5` (`exception.rs:250-251`). That is exactly the pattern behind the multi-day S3 bug.
  - `save_slice_frame` uses 31 hand-written offsets (`sched/mod.rs:1493-1507`) → Q1.
- **H5. Use-after-free and leaks on teardown:**
  - `close_all_for_pid` frees window frames without unmapping them ✔. They stay EL0-writable through the global window mirror (`user_windows.rs:370-376`), which every app can see.
  - Reaping frees the user stack while it is still mapped (`sched/mod.rs:1588` vs `elf.rs:480`).
  - Each run leaks its page tables, ELF image and heap: `destroy_address_space` (`process_vmem.rs:198`) is never called from reap.
  - `sys_win_close` unmaps only in the caller's page table (`user_windows.rs:412-423`); the two teardown copies have drifted apart → Q4.
- **H6. No user-pointer validation anywhere.** For example, `sys_win_create` dereferences the title pointer directly (`user_windows.rs:251-252`) → Q4.
- **H7. Login without authentication.** The greeter never calls `verify_password`, and root's default password is empty (`users/mod.rs:40`) → Q14.
- **H8. The kernel panics from a UI action.** Calculator `%` by zero, and also `i64::MIN / -1` → Q1.

### 2.3 Medium severity, and confirmations
- **`kill()` doesn't stop a running task** (`sched/mod.rs:1547-1560`). Worse, the background sleep path marks the zombie Ready again (`syscall.rs:1200`). The default signal "terminate" action has the same bug (`signal.rs:305-313`).
- **A re-entrancy hazard with foreground apps.** An app launched from serial gets a full `wm::tick` nested inside `sys_sleep` (`syscall.rs:1213`). That tick runs router and panel actions that `input.rs:170-173` says must not run in syscall context. `run_and_wait` has a single save area (`KERNEL_CALLEE_SAVE`, `sched/mod.rs:1260-1261`), so a launcher click during a foreground app would re-enter it.
- **Deferred clicks land in the wrong place.** They replay at the cursor position at replay time, not at click time (`input.rs:237-240,391`). On ring overflow a press can be dropped while its release is kept (`input.rs:64-68`).
- **The S4 claim "hit_test already topmost-first" is false.** `user_windows::hit_test` checks slots in index order and ignores z-order (`user_windows.rs:466-491`), and the user-window stage runs before window chrome (`event_router.rs:85`). A click on a window drawn over an EL0 app goes to the app underneath.
- **Ticks are counted twice, without locking:**
  - The main loop still calls `on_timer_tick` every 1 ms (`lib.rs:1008-1024` ✔) on top of the 10 ms IRQ.
  - `TICK_COUNT` is a plain `static mut` written from both contexts.
  - `TASK_TABLE` is modified from the IRQ (`sched/mod.rs:1019-1053`) and from the main loop (`:1592`) without masking interrupts.
- **The slice-yield marker is passed in-band:** an exit code of `0x5E5_0000` is treated as a yield (`sched/mod.rs:1384,1466`).
- **The Linux-compatible syscall table has 10 duplicate numbers** (`syscall.rs:614-704`). For example FSTATFS and TRUNCATE are both 45, so truncate silently succeeds without truncating (`:759`). The native table is fine (102 constants, 102 distinct values).
- **The idle loop busy-spins** for 33 ms instead of waiting for an interrupt (`lib.rs:1044-1054` ✔). Each idle VM therefore pegs a host core at 100%, and the dev host is the Pi 5 itself, shared by parallel sessions.
- **Debug prints in hot paths** (the skill's own rules warn these change TCG timing):
  - The first 5 timer ticks (`exception.rs:286`).
  - Every EL0 data abort (`:159`).
  - Every slice (`sched/mod.rs:1280`).
  - `signal.rs:340` and `elf.rs:357`.
- **The kernel is effectively single-core:**
  - On QEMU the secondary cores sit idle at EL3 (`boot.S:33-51`), and SMP start-up returns early (`smp/mod.rs:278-286`).
  - On real hardware they would run `core_scheduler_loop` against an unlocked `TASK_TABLE` (`smp/mod.rs:341`).
- **Crate-wide lint allows hide problems.** `lib.rs:7-50` allows `dead_code`, `static_mut_refs`, `unused_results` and `unused_must_use`, plus about 38 clippy lints.
- **Dead or stub code:**
  - `restore_kernel_regs` is empty (`sched/mod.rs:1342`).
  - Never called: `mirror_user_mappings` (`elf.rs:664`), `dl_resolve`, the App Store render function, `highlight_line`, both clipboards.
  - `SNAP_PREVIEW` is never set.
  - Never read: `btn_border_radius`, `FrameStats.fps`, `theme::FontSize`.
  - No callers: calculator `handle_click` and editor `feed_key`.
- **A leftover identity bug:** `shell/mod.rs:3361` still has `let current_user = "root"; // TODO` after C5.
- **These checked out fine:**
  - **S1:** ADVANCE_HEAD (0x1C) and CLEAR (0x18) no longer collide (`lobster_input.c:409-421`; the guest writes 0x1C at `qemu_input.rs:126`). Neither side's register docs mention 0x1C yet.
  - **C2:** the routing table really is the dispatch path. Its only callers are `input.rs:363/395/400`, and no old parallel dispatch remains.
  - **C3:** the `/home/user` alias uses whole-component matching (`vfs.rs:525-534`).
  - **C8:** the argv block is capped at 4 KB (`sched/mod.rs:632-669`).

## Deliverable 3: Ordered execution queue

### 3.0 Decisions and lanes
- **Should B7 (Code app) jump the queue? It shouldn't go ahead of Q3–Q5, but it should go ahead of everything else, and its UI should be built in parallel from day one.**
  - Code being written usually loops or crashes. Today any program that doesn't sleep freezes the whole OS with no Ctrl+C (H1), and running it next to another app can corrupt both (H2).
  - A flagship that hangs the desktop on the first `while(1);` would undermine the north star.
  - The editor and output-pane work (Lane U) and the QEMU chunked-compile work (Lane T) don't conflict with the kernel lane, so the Code app can merge the day Q5 lands.
- **Is E2 worth measuring now? Yes; it's part of Q2 (size S).**
  - The instrumentation carries no risk.
  - It records a baseline before Q3–Q5 change the boot path.
  - It lets the harness wait for a "desktop-ready" marker instead of a fixed 16 s sleep, which D7 also needs.
  - Replacing the >100-tick splash rule with a time-based hand-over removes at least 3.3 s of delay the guest imposes on itself.
  - Deeper optimisation waits until Q18.
- **Lanes.** Numbers give priority and merge order. Different lanes can run at the same time in separate worktrees; within a lane, go in order.
  - **K (kernel, one session at a time; the parent verifies live before each merge):** Q1(c–h) → Q3 → Q4 → Q5 → Q6.
  - **U (apps):** Q1(a,b) → Q7 → Q8-UI → Q9 → Q10 → Q11 → Q12 → Q13 → Q14 → Q15 → Q16 → Q17 → Q23 → Q24 → Q25.
  - **T (tests and emulator):** Q0 → Q2 → Q19 → Q20 → Q8's QEMU part → Q21 → Q22.
  - Rebase every lane on master after each Lane K merge.
  - New shell hooks go in new files, because the 6,508-line `shell/mod.rs` is a merge-conflict hotspot.
  - For every K item, write the failing acceptance test first, and never ship from a build with debug instrumentation.
